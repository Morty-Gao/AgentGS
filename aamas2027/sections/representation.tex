\subsection{Hierarchical Representation and Skill Hypergraphs}
\label{sec:representation}
AgentGS represents strategies, reusable operations, and implementations as Skills, Capabilities, and Tools. This separation supports operation reuse and preservation of constraints. Figure~\ref{fig:overview}(b) shows their relationships.

\paragraph{Skill.}
A Skill describes a reusable strategy for a class of tasks: its objective, applicable inputs, expected artifacts, capability steps, constraints, validation requirements, and recovery policies. Each step references a Capability and specifies mandatory predecessors, mandatory or optional status, and permitted tools. The system selects task-relevant local steps rather than executing the entire strategy unchanged. Generating a new Skill means organizing a newly composed capability workflow into a strategy description; this does not create new Capability definitions or Tool implementations.

\paragraph{Capability.}
A Capability describes an operation shared across strategies, including its function, input/output types, preconditions, postconditions, and candidate tools. For example, deep-time geoscience and carbon-storage strategies can share a raster-analysis capability while permitting different tools. Sharing an operation therefore preserves its strategy-specific usage constraints. Capability--Tool mappings record concrete implementations and parameter constraints to distinguish tools with similar functions. A Capability can have multiple implementing Tools, and a Tool can implement multiple Capabilities.

\paragraph{Tool.}
A Tool is a callable interface for computation or data processing. Its registration includes an identifier, parameter schema, input/output definitions, and runtime information. Concrete files, values, and upstream artifacts are bound during execution.

Skill--Capability membership and Capability--Tool implementation relationships are both many-to-many. The former identifies the operations in a strategy; the latter identifies candidate implementations. Actual tool selection and executability additionally depend on the task, capability-instance constraints, and runtime conditions.

This representation establishes an operational workflow while retaining each reused capability's constraints. A task plan uses capability instances to record the identity, provenance, and input role of each operation:
\begin{equation}
P=(V,D_d,D_c,\beta),\qquad v_i=(c_i,s_i,r_i).
\label{eq:plan}
\end{equation}
Here, $V$ contains capability instances; $c_i$ identifies the operation, $s_i$ records its source strategy, and $r_i$ identifies the step and input role. $D_d$ and $D_c$ record data and control dependencies, while $\beta$ binds inputs to task resources or upstream artifacts. The plan thus specifies both execution order and the data consumed by later steps. Operations on different input objects remain distinct instances, even when they use the same tool; functional similarity alone does not justify merging them.

Shared Capabilities connect different Skills. A skill hypergraph built from registered Skills represents Capabilities as nodes and each Skill's capability set as a hyperedge:
\begin{equation}
H=(C,E),\qquad E=\{e_s:s\in S\},\qquad e_s\subseteq C.
\label{eq:hypergraph}
\end{equation}
For example, Skills $S_1$ and $S_2$ containing $\{a,b\}$ and $\{b,c\}$ share node $b$. Membership identifies the operations contained in a Skill, but execution order additionally requires expanding the conditions governing their dependencies. Execution prerequisites are represented separately by the provenance-bearing relation $d=(s,U,c)$: within Skill $s$, operation $c$ requires all predecessors in $U$.

The hierarchy connects strategies, shared operations, and implementations while retaining the conditions under which operations are reused. Planning uses this information to determine the current workflow; completion uses it to assess whether missing steps can be connected.
