\section{System Architecture and Implementation}
\label{sec:system}
A task can require not only statistical and comparison tools but also propagation of statistics to later operations. AgentGS integrates the planning and completion methods of \papersection{sec:method}{3} into an interactive system. The frontend receives questions and task resources; plans, invocation records, and feedback are retained during execution, making the processing underlying an answer available for inspection.

\subsection{Overall Architecture}
\label{sec:architecture}
Figure~\ref{fig:architecture} shows four components: an interactive frontend, an agent orchestration service, knowledge and capability resources, and a tool execution service. Users submit natural-language questions and resources through the frontend. Orchestration retrieves Skills, organizes capabilities and dependencies, completes missing operations, and forms a capability plan. Knowledge and capability resources supply strategies, capability-to-tool mappings, and tool associations. Concrete tools are invoked by the execution service through a unified interface.

After planning, orchestration selects tools satisfying each capability instance's constraints and delegates calls to execution. The execution service accesses interfaces by tool identifier, supplies parameters and resources, and returns results or failure information. Orchestration decides whether to continue or handle failure under \papersection{sec:execution}{3.5}. Answers and feedback return to the frontend, connecting planning, execution, and result presentation within one task.

\subsection{Tool Integration and Data Propagation}
\label{sec:tool-integration}
The system separately maintains strategy operation definitions, capability-to-tool mappings, and invocation interfaces. Integrating a tool registers its function, parameters, and input/output information and associates it with Capabilities. The containing Skill constrains prerequisites and candidate tools. Task-specific selection checks functional matching, instance constraints, and interface compatibility with the current inputs.

Correct use of preceding results depends on binding parameters to artifacts actually generated. Intermediate artifacts retain their types and provenance, including the generating tool, step, and metadata. Artifact references bind files or results to later parameters. For example, statistics receives the target raster, and comparison receives the value from that statistical operation. File inputs and numerical inputs are bound separately, avoiding reliance solely on natural-language data descriptions and preserving provenance in execution records.

On failure, preceding successful steps and results are retained, and retry rules and instance constraints govern the failed call. Parameters, return states, and recovery attempts are stored to trace propagation and locate failures. Attempt limits, substitution scopes, and conditions prohibiting automatic replay are given in \papersection{sec:execution}{3.5}.

\subsection{Interactive Interface and Process Inspection}
\label{sec:interface}
The frontend supports task dialogue, tool-graph browsing, and configuration management. After receiving an answer, users can expand the records in Figure~\ref{fig:interface} to inspect plans, invocation inputs and outputs, execution states, attempt counts, and explanations. These records help check whether a tool read the intended file and whether later steps used the corresponding upstream outputs. Questions, answers, and traces are retained in history for retrospective analysis.

The graph interface shows GeoToolKG tools as nodes and recommended transitions as edges. Selecting a node reveals its function, inputs, outputs, provenance, and recommended successors. Edges provide retrieval and workflow-understanding cues; the capability plan, instance constraints, and execution conditions determine whether those transitions are used in a specific task.
